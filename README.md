# Threat Exchange Service

REST-сервис на Go для обмена информацией об угрозах по MD5-хешу файла. Клиенты могут создавать записи, получать сведения об угрозе и заменять ранее сохранённые данные через JSON API.

## Что реализовано

**Три операции REST API:**

| Операция | Поведение |
| --- | --- |
| `POST /info` | Создаёт запись с уникальным MD5. При успехе возвращает `201`, сохранённую запись и заголовок `Location`. Повторное создание того же MD5 возвращает `409`. |
| `GET /info/{md5}` | Возвращает полную запись с кодом `200`. Если запись отсутствует — `404`, если MD5 некорректен — `400`. |
| `PUT /info/{md5}` | Полностью заменяет изменяемые поля существующей записи и возвращает `200`. Сохраняет MD5 и дату создания; пропущенные необязательные поля сбрасывает к значениям по умолчанию. Если записи нет — `404`. |

Дополнительно предусмотрен `GET /healthz`: он проверяет соединение с БД и возвращает `200` или `503`. Этот маршрут доступен без токена.

В записи можно указать название угрозы, описание, категорию, уровень опасности и время обнаружения. Обязательны только `md5` и `name`, поэтому для начала достаточно передать хеш и название. Даты создания и последнего изменения сервер заполняет сам.

Перед сохранением сервер проверяет JSON и значения полей: например, не пропустит неправильный MD5, пустое название или время обнаружения в будущем. Запрос с ошибкой не меняет данные. Подробные правила и коды ответов приведены в разделе «API и модель».

Данные хранятся в файле SQLite и остаются доступными после перезапуска. Схема БД создаётся автоматически при первом запуске. Если несколько клиентов одновременно создают запись с одним MD5, база сохранит только одну, а остальные запросы получат `409`. Для запуска не нужен отдельный сервер БД.

Для чтения и изменения угроз нужен Bearer-токен. Сервис ограничивает частоту запросов, размер тела и время обработки; при превышении лимита запросов отвечает `429`. Для HTTPS можно задать свой сертификат и ключ. Подробности внутренних ошибок остаются в логах сервера, а токены и тела запросов в логи не записываются.

API описан в OpenAPI. По этой спецификации `oapi-codegen` создаёт Go-модели запросов и ответов. Проверки полей и настроек покрыты unit-тестами, а операции с данными и HTTP проверяются с настоящей SQLite и локальным сервером. Для запуска в контейнере подготовлены Dockerfile и Compose; файл БД хранится в отдельном томе.

## Быстрый запуск

Нужен Go **1.24+**

Для примеров запросов нужны `curl` и `openssl`. Из корня проекта в Bash или Zsh:

```bash
# Случайный токен на текущую сессию; сохраните его для запросов во втором терминале.
export API_TOKEN="$(openssl rand -hex 32)"
printf 'API_TOKEN=%s\n' "$API_TOKEN"
go run ./cmd/server
```

По умолчанию сервер слушает `http://127.0.0.1:8080`, БД создаётся в `data/threats.db`. `Ctrl+C` запускает корректное завершение с ожиданием текущих запросов.

Если удобнее запускать собранное приложение:

```bash
go build -o bin/server ./cmd/server
./bin/server
```

Переменная `API_TOKEN` должна быть задана и при запуске бинарного файла.

Для примеров откройте второй терминал и задайте **тот же** токен:

```bash
export API_TOKEN='токен-из-первого-терминала'
BASE_URL='http://127.0.0.1:8080'

curl --fail "$BASE_URL/healthz"

# Создание: HTTP 201.
curl -i "$BASE_URL/info" \
  -H "Authorization: Bearer $API_TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary @examples/create.json

# Получение: HTTP 200.
curl -i "$BASE_URL/info/d41d8cd98f00b204e9800998ecf8427e" \
  -H "Authorization: Bearer $API_TOKEN"

# Полная замена: HTTP 200.
curl -i -X PUT "$BASE_URL/info/d41d8cd98f00b204e9800998ecf8427e" \
  -H "Authorization: Bearer $API_TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary @examples/update.json
```

Повторный POST того же MD5 вернёт 409. Сведения сохраняются после остановки и повторного запуска сервера с тем же `DB_PATH`.

## Запуск через Docker

Нужны Docker с поддержкой Linux-контейнеров и Docker Compose v2. Команды подходят для Linux и macOS; на macOS Linux-контейнер запускается через виртуальную машину Docker.

```bash
cp .env.example .env
# Заменить API_TOKEN=replace-me в .env случайным токеном (не менее 32 символов).
# Например, сгенерировать его командой: openssl rand -hex 32
docker compose up --build -d
curl --fail http://127.0.0.1:8080/healthz
```

В `.env` задайте настоящий токен вместо `replace-me`: с коротким значением из примера сервер не запустится. Если `API_TOKEN` уже экспортирован в терминале, Compose использует его вместо значения из `.env`. При запуске через `go run` файл `.env` не читается — нужны переменные окружения.

После запуска можно использовать примеры `curl` из предыдущего раздела с тем же токеном, который передан контейнеру.

Посмотреть логи и остановить сервис:

```bash
docker compose logs -f api  # Ctrl+C завершает просмотр логов
docker compose down
```

Данные находятся в томе `threat-data`. Обычный `docker compose down` сохраняет их, а `docker compose down -v` удаляет вместе с томом. Контейнер работает от непривилегированного пользователя: корневая файловая система доступна только для чтения, а `/data` — для записи. Порт опубликован только на localhost. В образе нет командной оболочки; доступность сервиса проверяется снаружи через `/healthz`.

## API и модель

Полный контракт: [api/openapi.yaml](api/openapi.yaml). Для POST/PUT требуется `Content-Type: application/json` (допустим `charset=utf-8`). Для всех `/info` требуется `Authorization: Bearer <API_TOKEN>`.

| Метод и путь | Назначение | Основные ответы |
| --- | --- | --- |
| `POST /info` | Создать уникальную запись | 201, 400, 409 |
| `GET /info/{md5}` | Получить запись | 200, 400, 404 |
| `PUT /info/{md5}` | Заменить существующую запись | 200, 400, 404 |
| `GET /healthz` | Проверить соединение с БД без токена | 200, 503 |

Общие ошибки: 401 — неверный токен, 413 — тело больше 16 KiB, 415 — неподдерживаемые Content-Type/charset/Content-Encoding, 429 — rate limit, 500 — внутренняя ошибка. Неизвестный путь даёт JSON 404, неподдерживаемый метод — JSON 405 с `Allow`. POST возвращает заголовок `Location`.

| Поле | Правило |
| --- | --- |
| `md5` | Обязателен только при создании: ровно 32 шестнадцатеричных символа. Регистр не важен, хранится в нижнем регистре. Используется как идентификатор записи. |
| `name` | Обязателен: 1–255 Unicode-символов после удаления внешних пробелов. |
| `description` | До 4096 Unicode-символов, по умолчанию пустая строка. |
| `category` | `unknown`, `virus`, `trojan`, `ransomware`, `spyware`, `worm`, `adware`, `other`; по умолчанию `unknown`. |
| `severity` | `unknown`, `low`, `medium`, `high`, `critical`; по умолчанию `unknown`. |
| `first_seen` | Необязательное время обнаружения в RFC3339, не в будущем. Отсутствует в ответе, если неизвестно. |
| `created_at`, `updated_at` | Серверные даты в UTC; клиент не может их задавать. |

Для создания достаточно `md5` и `name`. PUT — **полная замена** изменяемых полей: если не передать `description`, оно станет пустым; `category` и `severity` станут `unknown`, а `first_seen` будет удалён. `md5` берётся из пути и не должен присутствовать в теле PUT. Дата создания сохраняется. Если записи нет, PUT возвращает `404`. При одновременных обновлениях сохраняется результат последнего выполненного UPDATE.

В теле запроса должен быть один JSON-объект размером не более 16 KiB. Неизвестные и повторяющиеся ключи, неверный регистр имён полей, `null`, некорректный UTF-8 и второй JSON-объект после первого приводят к ошибке. Повторные ключи проверяются и после раскрытия Unicode-экранирования. NUL в `name` и `description` запрещён; год `first_seen` после перевода в UTC должен оставаться в пределах 0000–9999. Пустая строка для `category` и `severity` недопустима. При ошибке данные остаются прежними.

Пример ответа:

```json
{
  "md5": "d41d8cd98f00b204e9800998ecf8427e",
  "name": "Trojan.Win32.Generic",
  "description": "Пример угрозы",
  "category": "trojan",
  "severity": "high",
  "first_seen": "2026-01-01T10:00:00Z",
  "created_at": "2026-10-24T12:00:00Z",
  "updated_at": "2026-10-24T12:00:00Z"
}
```

Ошибка: `{"message":"Threat not found"}`. При ошибках полей `details` содержит безопасное пояснение; SQL-ошибки и секреты клиенту не передаются.

## Конфигурация

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `API_TOKEN` | нет, обязательна | Непустой токен без пробелов, не менее 32 байт. |
| `HTTP_ADDR` | `127.0.0.1:8080` | Адрес сервера; в контейнере `:8080`. |
| `DB_PATH` | `data/threats.db` | Путь к файлу SQLite; родительский каталог создаётся. |
| `RATE_LIMIT_RPS` | `20` | Сколько разрешений на запрос добавляется в секунду; положительное конечное число. |
| `RATE_LIMIT_BURST` | `40` | Максимальный запас разрешений для короткого всплеска запросов. |
| `TLS_CERT_FILE` | пусто | Путь к PEM-сертификату/цепочке. |
| `TLS_KEY_FILE` | пусто | Путь к PEM-ключу; задаётся вместе с сертификатом. |

Для HTTPS задайте пути к сертификату и ключу; минимальная версия TLS — 1.2. По умолчанию HTTP доступен только на `127.0.0.1`. Для публичного доступа включите HTTPS в сервисе или на обратном прокси. Если HTTPS обслуживает прокси, ограничьте прямой доступ к HTTP-порту приложения. В Docker сертификат и ключ нужно подключить как файлы только для чтения и указать пути внутри контейнера.

При проверке токена сравниваются его SHA-256-дайджесты за постоянное время. Все владельцы токена имеют одинаковые права чтения и записи. Лимит запросов общий для процесса: по умолчанию разрешения пополняются со скоростью 20 в секунду, а накопить можно до 40. Запросы с неверным токеном также расходуют этот запас; `/healthz` исключён. При превышении сервер возвращает `429` и `Retry-After`. Лимит не зависит от IP и заголовка `X-Forwarded-For`.

## Тесты, сборка и генерация

```bash
go test ./...
go vet ./...
go test -coverprofile=coverage.out ./...
go build -o bin/server ./cmd/server
go generate ./api
```

Для тестов Docker не нужен: каждый интеграционный тест получает отдельную файловую SQLite во временном каталоге. HTTP-тесты отправляют запросы локальному `httptest.Server`. Они проверяют создание, чтение и замену записей, ошибки запросов, сохранность данных, одновременное создание одного MD5, проверку токена и ограничение нагрузки. Отдельно проверяются правила полей, настройки и соответствие ответов OpenAPI.

Нормализацию MD5 можно дополнительно проверить на случайно сгенерированных входных данных. Также предусмотрен запуск с детектором гонок:

```bash
go test ./internal/threat -fuzz=FuzzNormalizeMD5 -fuzztime=10s
go test -race ./...
```

## Структура и решения

```text
api/                 OpenAPI и настройки генерации
cmd/server/          запуск, TLS, сигналы и graceful shutdown
internal/api/        сгенерированные транспортные модели
internal/config/     чтение и валидация переменных окружения
internal/threat/     модель, нормализация и бизнес-валидация
internal/store/      SQLite, миграции, CRUD и интеграционные тесты
internal/httpapi/    HTTP, JSON, авторизация, rate limit, HTTP-тесты
examples/            готовые JSON-запросы
docs/                устройство сервиса и результаты проверок
```
